# План работ №2 — объединение frontend_new и ИИ-модуля «ИИ для проекта (2)»

## Исходная ситуация

- **backend_new** — FastAPI REST API (`/api/v1`) учебного тренажёра: JWT + роли,
  PostgreSQL (Alembic), пользователи, справочники, задачи, сценарии, тренировки,
  эмулятор (runtime), карточки, отчёты, материалы, системные окна.
  ИИ-генерация — заглушка 501 (`/study-tasks/{id}/generate`), но в БД уже заложены
  поля `ai_score`, `ai_eval_details`, `machine_eval_details`, `field_schema` у карточек.
- **frontend_new** — тестовый статический фронт (HTML + CSS + чистый JS, без сборки):
  13 страниц, все 36 окон ТЗ реализованы и подключены к backend_new
  (REST-клиент с JWT в `app.js`, экранирование, «Сервер недоступен» без бэкенда).
- **ИИ для проекта (2)** — итоговый внешний вид: React 19 + esbuild (сборка раздаётся
  Python-сервером web_ui.py на 8878), свой action-based REST-контракт без JWT,
  данные в localStorage (`giik.card-workshop.v1`, training-plans) и файлах `data/`.
  Ценное: серверное ИИ-ядро (ai_core, provider — OpenAI/GigaChat/Gemini/Anthropic,
  card_factory, card_caller, card_reference, dds), ключ модели не попадает в браузер;
  клиентские виджеты: локальный OSM-поиск адресов + карта (ui/geo/), голосовой ввод
  (Web Speech), озвучивание (Piper + speechSynthesis), зависимый классификатор
  (1283 кода, 24 группы, 61 служба), баннеры, дизайн по SVG-макетам (theme.css и др.).

## Сравнение вариантов реализации

### Вариант 1: прикрутить REST API backend_new к проекту «ИИ для проекта (2)»
- Требует одновременно трёх переписываний:
  1. React-сборка → статическая структура frontend_new (переписать ~30 JSX-компонентов на vanilla JS);
  2. localStorage + action-API → JWT + REST backend_new (полная замена слоя данных);
  3. отсутствие авторизации → JWT + роли (с нуля).
- Покрытие окон ТЗ частичное: пользователей, справочников, отчётов, системных окон нет — писать с нуля.
- ИИ-ядро всё равно переносить в backend_new (фронт обязан обращаться только к его API,
  а ключ модели не может жить в браузере) — эта работа одинакова в обоих вариантах.
- Риск высокий: три переписывания одновременно, каждое следующее блокируется предыдущим.

### Вариант 2 (рекомендуется): frontend_new как основа, к нему переносится внешний вид и инструменты ИИ-проекта
- Структура, REST-клиент, JWT-авторизация и все 36 окон уже работают.
- Перенос дизайна — механическая работа: CSS-токены (theme.css) + разметка из JSX как эталон.
- Клиентские виджеты переносятся напрямую (адрес/карта, голос, баннеры — чистый JS без сервера).
- ИИ-ядро переносится на сторону backend_new (это всё равно обязательно).
- Каждый шаг инкрементальный и проверяемый; риск низкий.

**Вывод: вариант 2.** Вариант 1 — тройное переписывание с потерей уже готовой объёмной
работы; вариант 2 сохраняет проверенную основу и добавляет ценные части ИИ-проекта.

## План работ

1. Перенести ИИ-ядро из «ИИ для проекта (2)» в backend_new (provider.py, ai_core.py,
   card_factory.py, card_caller.py, card_reference.py, dds.py) как сервис app/services/ai/
   с настройками провайдера и ключа (env/config, ключ не выдаётся браузеру).
2. Реализовать ИИ-endpoints в backend_new: замена заглушки 501 в /study-tasks/{id}/generate,
   реплика заявителя, превью эталона, валидация полей карточки, предварительная оценка ИИ
   (запись в ai_score/ai_eval_details), проверка доступности ИИ.
3. Уточнить структуру итоговой БД, которая опиралась бы на структуру проекта backend_new, но
   учитывала бы в том числе и особенности реализации в "ИИ для проекта (2)".
4. Согласовать маппинг полной карточки ИИ-проекта на JSONB content + field_schema
   backend_new; UI зависимого классификатора подключить к существующим endpoints /classifier/*
   (классификатор из ИИ-проекта не переносить — у backend_new уже есть свои endpoints).
5. Перенести дизайн: токены ui/theme.css в frontend_new/style.css, затем постранично
   адаптировать workspace.css, cards.css, student.css, address.css по разметке JSX-компонентов.
6. Перенести клиентские виджеты: адресный поиск и карта (address-search.js + ui/geo/),
   голосовой ввод и озвучивание, баннеры ui/banners/.
7. Обновить страницы frontend_new: tasks.html (мастерская + генерация ИИ),
   trainings.html (workspace преподавателя), simulator.html (панель ученика и ДДС),
   cards.html (журнал), system.html (мониторинг ИИ).
8. Проверка: тесты backend_new, запуск START.cmd, прохождение сценариев 1–4 ТЗ,
   smoke-проверка реальной генерации ИИ и диалога заявителя.

## Ключевые правила реализации

- Ключ ИИ-провайдера — только в настройках/env backend_new, никогда в браузере
  (требование README ИИ-проекта).
- localStorage оставить только для черновиков и UI-настроек; хранилища giik.*,
  data/, web_ui.py, rest_api.py, api_contract.py и React-сборку НЕ переносить —
  их роли закрывают backend_new + статические страницы.
- Контракт карточек: генератор ИИ выдаёт content + field_schema в формате backend_new,
  чтобы эмулятор и журнал работали без конвертаций на клиенте.
- Соответствие страниц: мастерская карточек → tasks.html, workspace преподавателя →
  trainings.html, панель ученика и ДДС → simulator.html, журнал карточек → cards.html,
  мониторинг ИИ → system.html.
