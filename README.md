# Тренажёр операторов и диспетчеров Системы-112

Команда **«Игры и Теория»** · Сибирская пожарно-спасательная академия ГПС МЧС России

Учебное программное обеспечение для подготовки операторов Службы 112 и
диспетчеров ДДС города Москвы, по техническому заданию ГБУ «Система 112».
Ветка `ivb/trainer` — полное работающее решение: бэкенд, интерфейс, модель
внутри контура, переносной комплект для Windows, сопроводительная документация.

Три роли — обучающийся, преподаватель, администратор; два режима обучения —
приём вызова оператором 112 и работа диспетчера ДДС с карточкой на АРМ-112.
439 автоматических тестов.

## Сильные стороны решения

### 1. Полная автономность, включая нейросеть

ТЗ пять раз повторяет требование работы «без доступа к внешним сетям» и
допускает дополнительные модули только «при условии сохранения изолированности
контура». Решение спроектировано под это требование, а не приспособлено к нему:

- **Языковая модель — внутри комплекса.** Qwen3 4B работает в контейнере `llm`
  (llama.cpp) или отдельным процессом в переносном комплекте. Ни одного
  внешнего адреса во время работы.
- **Модель не стоит в критическом пути.** Балл и нарушения считает
  классификатор; модель пишет смысловой разбор, отвечает за заявителя
  в уточняющем диалоге и формирует новые сценарии. Недоступна модель —
  занятие идёт, оценка выставляется.
- **Качество модели измерено**, а не предположено: на 15 размеченных примерах
  (`backend/scripts/compare_llm.py`) Qwen3 4B точна в 14, пропусков нет,
  орфографию находит в 2 случаях из 3; облачный GigaChat орфографию
  не находил вовсе.
- **Проверено на месте.** Переносной комплект запущен на рабочем месте под
  Windows 10 без Docker и без прав администратора, в Яндекс.Браузере и Edge,
  с доступом учеников по локальной сети.

### 2. Живые голоса заявителей

Все 96 экзаменационных вызовов Службы 112 озвучены — но не одним голосом.
Каждый вызов записан **тремя голосами того же пола, что и заявитель**:
пол определяется по ФИО из билета, а если имени нет — по тексту («вызывает
мама», «вызывает супруг»). Десять голосов — пять мужских и пять женских,
отобранных на слух, от трёх локальных синтезаторов (Piper, Silero, macOS).
Третий вариант каждого вызова звучит «по телефону» — узкая полоса и шум.

Голос выбирается случайно и закрепляется за попыткой: при повторном
прослушивании тот же, у соседа по классу — другой. Обучающийся привыкает
к разным тембрам, темпу и плохой связи, как в настоящей смене. Синтез
выполняется при сборке; заказчику уходят готовые MP3, синтезатор не нужен.

Сверх записи — **диалог с заявителем**: обучающийся может спросить то,
чего не услышал («какой подъезд?», «есть пострадавшие?»), модель отвечает
за заявителя строго по обстоятельствам вызова и на неизвестное говорит
«не знаю».

### 3. Классификатор — документ заказчика, а не схема данных

Эталон в тренажёре задаёт Единый классификатор происшествий: 1283 правила,
23 группы, 58 служб, 17 признаков, меняющих список оповещения. Это документ,
который заказчик ведёт в Excel и правит раз в год, а приложение только читает.

Поэтому ЕКП не раскладывается по нормализованным таблицам (группы, признаки
трёх уровней, классы событий, связи со службами). Файл `classificator.xlsx`
разбирается целиком в один машинно-читаемый документ, и новая редакция
загружается администратором **как новый документ**: занятие фиксирует
редакцию, по которой шло, и через год оценивается по ней же. Для справочника,
который только читается и меняется целиком, это проще и надёжнее шести
связанных таблиц, их миграций и синхронизации с исходным Excel. Реляционная
база (PostgreSQL) остаётся там, где она действительно нужна: пользователи,
занятия, попытки, оценки, журнал аудита.

Отсюда и главное свойство оценки — **детерминированность**: одни и те же
признаки всегда дают один и тот же тип и список оповещения, и балл
не зависит от того, какая модель подключена.

### А также

- **Карточка по образцу настоящего АРМ-112** — компоновка по скриншоту
  рабочей системы: телефоны и таймер, адрес по частям, кнопки признаков
  «Пострадавшие», «Нет на месте», «Нет доступа», классификатор, полоса
  служб, заполняющаяся по мере выбора.
- **Разбор объясняет, а не только оценивает**: какие службы не выехали бы
  из-за ошибки, почему каждая служба в списке оповещения, и цитата из речи
  заявителя к каждому замечанию об адресе, телефоне и признаках.
- **Итоговое решение за преподавателем**: машинная оценка — предложение,
  преподаватель ставит итоговый балл с обоснованием, изменение пишется
  в журнал аудита.
- **Реальный учебный материал**: 32 экзаменационных билета, 96 вызовов,
  расшифрованы дословно; 79 заведены в занятия — с классификацией, передачей
  по принадлежности и отказом в регистрации.

### Что сознательно не сделано

| Пункт ТЗ | Почему |
|---|---|
| Обработка вызовов через VoIP, настройка VoIP, локальный SIP-сервер | Вызов имитируется записью голоса и диалогом с заявителем. Телефония без реальной АТС учебного центра была бы декорацией, а её настройка — вне сроков и вне проверяемого |
| Многоуровневая аутентификация | Один фактор — логин и пароль с защитой от перебора. Второй фактор в изолированном контуре требует своей инфраструктуры (токены, SMS-шлюз), которой у заказчика не описано |
| XML для конфигураций и методических материалов | Конфигурация — переменные окружения и JSON, материалы — текст и файлы. Отдельного потребителя XML в контуре нет |
| PDF-сертификаты | Отчёты и документация выгружаются в PDF; формы сертификата в ТЗ нет, выдумывать её не стали |
| Мобильная вёрстка узких экранов | Карточка АРМ-112 по своей природе рассчитана на широкий экран. Планшеты ТЗ допускает в настольном режиме; телефоны не проверялись |
| Аттестация по ИБ, проверка на оборудовании заказчика | Требуют заказчика: реализованы RBAC, аудит, TLS, защита от перебора; требования к оборудованию соблюдены |

Частично — по замыслу: запуск и остановка сервисов, расписание резервного
копирования и политики доступа управляются конфигурацией развёртывания,
а не кнопками в интерфейсе администратора; оповещения о сбоях видны
в разделе «Состояние», но не рассылаются почтой.

## Предлагаемые улучшения

1. **Адресный справочник и карта.** Геокодер Photon с заранее собранным
   индексом Москвы и области (OpenStreetMap) — отдельным контейнером, без
   сети: подсказки адреса при вводе, поиск безадресных объектов («ТЦ Вегас»,
   «станция метро Арбатская»), точка на карте в разборе. Прежде чем встраивать —
   замерить долю найденных адресов на 96 вызовах билетов.
2. **Режим «Обучение» с подсказками.** По идее руководителя команды: после
   нескольких секунд бездействия — подсказка у поля («Уточните подъезд и код
   домофона»), по кнопке — точнее («Заявитель назвал подъезд — вы его не
   записали»). Подсказки учитываются в отчёте преподавателя. Реализуется без
   модели.
3. **Порог грамматических ошибок в зачёте**, задаваемый преподавателем, —
   с «предварительным» зачётом, пока фоновая проверка моделью не пришла.
4. **Эталоны для оставшихся 17 вызовов** билетов, где классификатор
   не дал однозначного правила, — разметка методистом.
5. **Карточки, составленные обучающимися**, как источник сценариев
   (сценарий 3 бизнес-процессов команды) и комментарий преподавателя
   к занятию целиком.
6. **Экспорт в XLSX** и мобильная вёрстка страниц обучающегося.

## Запуск

### Переносной комплект для Windows — без Docker и без установки

`scripts/package_portable.sh` собирает `dds112-portable.zip` (≈ 2,7 ГБ):
встраиваемый Python, PostgreSQL 17, llama.cpp с моделью, код и интерфейс.
На месте — распаковать на диск и дважды щёлкнуть `start.cmd`; прав
администратора не нужно, база и журналы — в `data\`. Доступ ученикам
из класса уже включён готовым `settings.cmd` (`set "WEB_HOST=0.0.0.0"`). Обновление —
`--update`, архив поверх папки; миграции применяются при запуске, перед ними
снимается копия базы. Подробно — [`docs/windows.md`](docs/windows.md).

### Контейнеры для учебного центра

Поставка — архив образов `dds112-images.tar` и папка `dds112-deploy`
с файлами развёртывания. На месте:

```bash
docker load -i dds112-images.tar
cd dds112-deploy && cp .env.example .env      # заполнить пароли и ключ
docker compose -f docker-compose.prod.yml -f docker-compose.offline.yml up -d
```

Обязательные переменные в `.env`: `DB_USER`, `DB_PASSWORD`, `DB_NAME`,
`SECRET_KEY`, `DEMO_PASSWORD`. Модель поднимается в контейнере `llm`,
суточные резервные копии снимает контейнер `backup`.

### Сборка поставки

Выполняется у разработчика; заказчику передаются только готовые архивы.

```bash
sh ops/llm/fetch_model.sh                     # файл модели для образа llm
sh scripts/package_offline.sh                 # архив образов под linux/amd64
sh scripts/package_portable.sh                # переносной комплект для Windows
sh scripts/package_portable.sh --update       # архив обновления комплекта
python backend/scripts/make_voices.py         # озвучка вызовов (на Mac)
```

### Разработка

```bash
docker compose up -d --build                  # PostgreSQL и API на localhost:8000
cd frontend && npm install && npm run dev     # интерфейс на localhost:5173
cd backend && python -m pytest                # 439 тестов
```

Учебные учётные записи — `admin`, `teacher`, `student`, `student2`; пароль
совпадает с логином, если не задан `DEMO_PASSWORD`.

### Модель

Провайдер переключается в интерфейсе администратора, без перезапуска:
`local` — любой OpenAI-совместимый адрес внутри контура (llama.cpp, vLLM,
Ollama); `gigachat` — внешний API; `stub` — без модели, всё работает, кроме
текстового разбора и диалога с заявителем.
