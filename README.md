# Тренажёр операторов и диспетчеров Системы-112

Учебное программное обеспечение для подготовки персонала дежурно-диспетчерских
служб города Москвы. Разработано по техническому заданию ГБУ «Система 112».

Рабочий стенд: **https://112.app-sibpsa.ru/**

---

## Главное: эталон задаёт классификатор, а не нейросеть

Тренажёр учит работе с реальным происшествием, поэтому «правильный ответ»
в нём не может быть мнением языковой модели. Эталон берётся из Единого
классификатора происшествий (ЕКП), который разобран из `classificator.xlsx`
в машинно-читаемый вид:

| | |
|---|---|
| правил классификатора | 1283 |
| групп происшествий | 23 |
| служб реагирования | 58 |
| признаков, меняющих список оповещения | 17 |

Каждое правило — это путь признаков («на улице» → «мусор» → «открытое пламя»),
итоговый тип происшествия («пожар: мусор») и список служб, которые обязаны
получить оповещение. Признаки вроде «пострадавшие» или «перекрытие движения»
список расширяют, но итоговый тип не меняют. Разбор целиком детерминирован:
одни и те же признаки всегда дают один и тот же результат.

**Что делает языковая модель.** Только то, что классификатором не проверить:
смысловой разбор комментария диспетчера и замечания к грамматике. Балл и
перечень нарушений она не выставляет. Если модель недоступна, занятие идёт
дальше и оценка выставляется полностью — без неё.

Такое разделение проверяемо. Мы прогнали пятнадцать размеченных примеров
из памятки через два провайдера (`backend/scripts/compare_llm.py`): по составу
замечаний GigaChat верен в 13 случаях, локальная Qwen3.6 — в 14, орфографию
GigaChat не находит вовсе, а локальная находит всю. Если бы от модели зависел
балл, эта разница означала бы разные оценки за одну и ту же работу.

## Два режима обучения

Технического задания касаются две разные должности, и тренажёр различает их.

### Оператор Службы 112 — приём вызова

Обучающийся слышит заявителя, ведёт опрос и сам классифицирует происшествие
по опросной карте: выбирает группу и последовательность признаков, вносит
адрес и описание.

Проверяется: правильность классификации, полнота списка оповещения (он
следует из выбранного типа автоматически), точность регистрации адреса,
своевременность. Нарушения — каталог `O1`–`O6`.

Разбор показывает не только «тип неверен», но и следствие: **какие службы
из-за этой ошибки не выехали бы на происшествие**.

### Диспетчер ДДС — работа на АРМ-112

Обучающийся получает готовую карточку происшествия и проставляет статус
реагирования: принять, отказать, отчитаться о ходе работ. Переходы между
статусами ограничены конечным автоматом по памятке ГБУ «Система 112».

Проверяется: соответствие статуса фактическому положению дел, соответствие
компетенции службы, своевременность, полнота комментария. Нарушения —
каталог `V1`–`V9`, с примерами из памятки.

### Два норматива времени

- **30 секунд** на взятие карточки в работу с момента поступления вызова;
- **3 минуты** на обработку одной карточки.

Нарушения нормативов — `V8` и `V9`. Нормативы задаются для каждого занятия
отдельно: преподаватель может их ужесточить.

### Многозадачность

Вызовы поступают потоком, параллельно, с заданным интервалом — обучающийся
ведёт несколько карточек одновременно и сам расставляет приоритеты. Это не
побочный эффект, а цель обучения: в реальной смене никто не работает над
одной карточкой до победного конца.

## Роли

| роль | что делает |
|---|---|
| **обучающийся** | проходит занятие, получает разбор своих ошибок |
| **преподаватель** | создаёт сценарии, утверждает их, ведёт занятие, смотрит отчёт |
| **администратор** | учётные записи, журнал аудита, состояние системы |

Сценарий не попадает к обучающимся, пока преподаватель его не утвердил.
Это относится и к сценариям, сгенерированным нейросетью, и к билетам,
эталон которых подобран машинно: **предлагает машина, решает человек**.

## Учебный материал

Расшифрованы все экзаменационные билеты Службы 112: **32 билета, 96 вызовов**,
дословно. Каждый вызов озвучен (`frontend/public/audio/`, MP3) — обучающийся
слышит заявителя, а не читает его реплику, как и бывает на приёме вызова.

К 59 вызовам подобрано правило классификатора; 50 из них выверены человеком
и утверждены, 9 оставлены преподавателю как черновики с указанием сомнения.
Остальные 37 в занятия не заведены — см. «Что не сделано».

## Запуск

### Разработка

`docker-compose.yml` поднимает базу и API; переменные окружения не нужны,
у всех есть умолчания, модель по умолчанию отключена (`stub`).

```bash
docker compose up -d --build      # postgres + API на localhost:8000
cd frontend && npm install && npm run dev
```

Интерфейс — `http://localhost:5173`. При первом запуске создаются схема
и демонстрационные данные: два идущих занятия, сценарии из памятки,
билеты Службы 112. Учебные учётные записи — `student`, `student2`,
`teacher`, `admin`, пароль совпадает с логином.

### Публикация

`docker-compose.prod.yml` добавляет третий контейнер: nginx раздаёт
собранный фронтенд и проксирует `/api`, поэтому всё на одном origin и CORS
не нужен. База портов не публикует, приложение слушает только петлевой
интерфейс — TLS и публичный доступ обеспечивает внешний nginx. Заданы
лимиты памяти и процессора: стенд живёт на общем сервере.

Обязательные переменные в `.env` (без них compose не стартует):
`DB_USER`, `DB_PASSWORD`, `DB_NAME`, `SECRET_KEY`, `DEMO_PASSWORD`.

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

### Тесты

```bash
cd backend && python -m pytest
```

117 тестов: разбор классификатора, конечный автомат статусов, оценка обоих
режимов, опросная карта, занятия, кабинеты, провайдеры ИИ.

## Настройка ИИ-провайдера

Контур переключается настройкой, код не меняется:

| `LLM_PROVIDER` | назначение |
|---|---|
| `gigachat` | внешний API, демонстрационный стенд |
| `local` | любой OpenAI-совместимый адрес: llama.cpp, vLLM, Ollama — изолированный контур |
| `stub` | без модели вовсе; система работает, смысловой разбор комментария недоступен |

Подробности и примеры — в `backend/.env.example`.

Для рассуждающих моделей предусмотрено отключение размышления
(`LLM_DISABLE_THINKING`): на проверке комментария это сокращает ответ
с 31 секунды до полутора и повышает точность.

## Что не сделано

Честный список, чтобы его не пришлось искать в коде.

1. **Передача вызова по принадлежности.** 20 из 96 экзаменационных вызовов —
   происшествия в других регионах. Правильное действие по ним — передача
   по принадлежности, а такого действия тренажёр пока не моделирует. Вызовы
   расшифрованы и озвучены, но в занятия не заведены: оценивать их
   классификацией значило бы учить неверному.
2. **17 вызовов без эталона.** Модель отказалась подбирать правило
   классификатора, когда подходящего не нашлось. Отказ здесь полезнее
   выдуманного ответа, но привязку нужно делать руками в кабинете
   преподавателя.
3. **Орфография в разборе комментария.** Замечания к грамматике текста
   обучающегося формируются и попадают в отчёт преподавателя, как требует
   ТЗ. Но GigaChat, который работает на стенде, орфографию не замечает —
   измерено, 3 ошибки из 3 пропущены, тогда как локальная модель нашла все
   три. Промпт требует доработки; инструмент замера готов
   (`scripts/compare_llm.py`). Сам набор примеров тоже узок: он проверяет
   написание слов, а ТЗ говорит о грамматике в целом — нужны согласование,
   падежи, управление.
4. **Принудительная проверка грамматики после правок преподавателя.**
   ТЗ предусматривает её в подготовке занятия: «проверка грамматики
   (при необходимости) — принудительная проверка после ручных манипуляций
   с данными». Правка сценария и коррекция через модель есть, проверки
   после них — нет.
