## 1. Постановка задачи (из `plans/database_structure.qmd`, этап 4)

Исходно требовалось:

1. При входе преподавателя прочитать `localStorage` `giik.card-workshop.v1`
   и перенести в таблицы `workshop_card` + `workshop_card_reference` +
   `workshop_card_version` + `workshop_card_event`.
2. Повторный импорт идемпотентен (по `workshop_card.id`/хешу).

### Решение команды (согласовано 2026-09-29)

**Минимальный объём: этап закрывается без реализации импорта.**

- Таблицы мастерской уже созданы на Этапе 2.2 (версия схемы `2.2.0`,
  [`catalog_repository.py`](../catalog_repository.py:92)) — дополнительного DDL не требуется.
- Данные в `localStorage` на текущем стенде — тестовые («грязные») записи;
  переносить их в «боевую» БД не нужно.
- Механизм переноса и работа мастерской с БД напрямую будут реализованы
  в рамках **Этапа 5** (переключение репозитория): хранилище мастерской
  перейдёт с `localStorage` на БД, `localStorage` останется только кэшем.

## 2. Обоснование (почему импорт не выполняется)

| Факт | Следствие |
|---|---|
| Мастерская хранит всё в `localStorage` конкретного браузера ([`workshop-store.js`](../frontend/src/workshop-store.js:6)) | Данные не являются общим источником истины |
| На стенде в браузерах лежат тестовые записи | Импорт замусорил бы БД, которая уже наполнена чистыми справочниками и учебными данными |
| Этап 5 переключит мастерскую на БД напрямую | Импорт накопленного станет не нужен: новые карточки сразу пишутся в БД; при желании миграция отдельных записей выполняется точечно через UI |

Дополнительно зафиксировано проектное ограничение (важно для Этапа 5):
импорт из `localStorage` в БД (если он всё же понадобится для переноса
наработанных карточек) должен быть **upsert-ом по уникальному `number`**
(не полной перезаписью таблиц), чтобы карточки из разных браузеров
не затирали друг друга.
