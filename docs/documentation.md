# Сопроводительная документация

**Учебный комплекс подготовки операторов и диспетчеров Системы-112**

Разработано по техническому заданию ГБУ «Система 112» города Москвы.
Рабочий стенд: <https://112.app-sibpsa.ru/>

---

## 1. Назначение

Комплекс предназначен для практической подготовки двух категорий персонала:

- **операторов Службы 112**, принимающих вызов и классифицирующих происшествие;
- **диспетчеров дежурно-диспетчерских служб**, получающих карточку происшествия
  на АРМ-112 и проставляющих статусы реагирования.

Обучающийся работает в имитации, неотличимой по логике от рабочей системы:
те же признаки происшествий, те же статусы, те же нормативы времени. Действия
сравниваются с эталоном и разбираются по каждой ошибке с указанием последствия —
какая служба не получила бы оповещения, куда ушла бы карточка.

Комплекс не обрабатывает реальные вызовы, не содержит функционала рабочей
системы-112 и не взаимодействует с внешними системами.

## 2. Функциональная архитектура

### 2.1. Роли

| Роль | Задачи |
|---|---|
| Обучающийся | проходит занятие, получает разбор, видит свой прогресс и историю ошибок, читает справочную базу |
| Преподаватель | готовит сценарии и утверждает их, собирает учебные группы, ведёт занятие, наблюдает за ходом, формирует отчёт и выгружает его, оставляет примечания к работам, ведёт справочную базу |
| Администратор | учётные записи и права, журнал аудита, состояние комплекса, его конфигурация |

Роли разведены строго и в обе стороны. Преподавателю закрыт кабинет
администратора, администратору — учебный процесс и персональные данные
обучающихся. Это требование технического задания, а не удобство: администратор
ограничен «в доступе к персональным данным пользователей без необходимости».

### 2.2. Два режима обучения

**Режим оператора Службы 112.** Обучающийся слышит запись обращения заявителя
и прежде всего решает, что с обращением делать. Исходов три:

| Исход | Когда |
|---|---|
| зарегистрировать происшествие | адрес в зоне ответственности Москвы |
| передать по принадлежности | происшествие в другом субъекте; называется субъект |
| не регистрировать | обращение не является происшествием для Системы-112 |

Только при первом исходе раскрывается опросная карта: обучающийся выбирает
группу происшествия и последовательность признаков, вносит адрес и описание.
Итоговый тип и список оповещения система выводит из признаков автоматически —
как это происходит в рабочей системе.

Порядок в интерфейсе повторяет порядок в работе намеренно. Опросная карта,
открытая сразу, подталкивает заполнять её не глядя на адрес, а экзаменационные
билеты проверяют ровно эту привычку: двадцать вызовов из девяноста шести —
происшествия в других субъектах либо обращения, происшествиями не являющиеся.

Проверяется решение об исходе, правильность классификации, полнота списка
оповещения, точность регистрации адреса, своевременность. Ошибки — каталог
`O1`–`O10`. Неверный исход обнуляет балл: карточка, заведённая на чужой
регион, может быть аккуратной и подробной, но силы реагирования о происшествии
не узнают, а система-112 своего субъекта — тем более. Обратная ошибка,
когда московское происшествие передано на сторону, наказывается так же:
на место не выедет никто.

**Режим диспетчера ДДС.** Обучающийся получает готовую карточку происшествия
и проставляет статусы реагирования: принимает заявку или отказывает, отчитывается
о ходе и завершении работ, сопровождает статусы комментариями.

Проверяется соответствие статуса фактическому положению дел, соответствие
компетенции службы, своевременность и полнота комментария. Ошибки — каталог
`V1`–`V9` с примерами из памятки ГБУ «Система 112».

### 2.3. Занятие

Занятие — единица учебного процесса: преподаватель задаёт состав обучающихся,
набор сценариев, нормативы времени и интервал поступления вызовов, затем
запускает занятие.

Вызовы поступают **потоком, параллельно**, с заданным интервалом. Обучающийся
ведёт несколько карточек одновременно и сам расставляет приоритеты. Это не
особенность реализации, а цель обучения: в реальной смене никто не работает
над одной карточкой до её закрытия.

Состав можно заполнить **учебной группой** — постоянным списком обучающихся
(набор курса, смена, поток), который преподаватель собирает один раз. Состав
при этом копируется в занятие, а не связывается с группой ссылкой: занятие —
событие, и правка группы через неделю не должна переписывать состав уже
проведённого занятия, а с ним и отчёт о нём.

Для занятия задаются **критерии успешности**: порог среднего балла
и допустимое число критических нарушений. По ним в отчёте проставляется зачёт.

Преподаватель может включить **возврат проваленных карточек**. Тогда карточка,
с которой обучающийся не справился — балл ниже порога занятия или критическое
нарушение, — выдаётся ему ещё раз в том же занятии, после остальных карточек
его потока: ошибка разбирается по горячим следам. Повтор назначается сразу
по детерминированной части оценки, не дожидаясь разбора языковой модели; повтор
повтора не выдаётся. В ленте обучающегося такая карточка помечена как повторная
выдача, эталон ей не раскрывается. Средний балл и зачёт считаются только
по первым попыткам, а по каждому повтору в отчёте и выгрузках видно, исправился
обучающийся или нет.

Во время занятия преподаватель видит ход в реальном времени: кому что выдано,
что открыто, что просрочено, что завершено. После завершения формируется отчёт
с действиями, замечаниями, временем обработки, отличием от норматива,
замечаниями к грамматике и выводами по типичным ошибкам группы. Отчёт
выгружается в CSV и PDF.

### 2.4. Нормативы времени

| Норматив | Значение по умолчанию | Нарушение |
|---|---|---|
| Взятие карточки в работу | 30 секунд от поступления | `V8` |
| Обработка одной карточки | 3 минуты от открытия | `V9` |

Тридцать секунд — требование постановления Правительства РФ № 1931, а не
произвольная настройка. Оба норматива задаются для каждого занятия отдельно:
преподаватель может их ужесточить.

## 3. Компонентная архитектура

```
        браузер обучающегося / преподавателя / администратора
                              │ HTTPS
                    ┌─────────▼──────────┐
                    │  внешний nginx     │  TLS, публичный адрес
                    └─────────┬──────────┘
                              │ HTTP, петлевой интерфейс
                    ┌─────────▼──────────┐
                    │  контейнер web     │  раздача собранного
                    │  nginx             │  интерфейса, проксирование /api
                    └─────────┬──────────┘
                              │
                    ┌─────────▼──────────┐        ┌──────────────────┐
                    │  контейнер backend │───────▶│  ИИ-провайдер    │
                    │  FastAPI, uvicorn  │        │  GigaChat или    │
                    └─────────┬──────────┘        │  локальная модель│
                              │                   └──────────────────┘
                    ┌─────────▼──────────┐
                    │  контейнер db      │
                    │  PostgreSQL 17     │
                    └────────────────────┘
```

Фронтенд и API работают на одном источнике: интерфейс раздаёт тот же nginx,
который проксирует `/api`. Поэтому кросс-доменных запросов в рабочей
конфигурации нет.

### 3.1. Состав серверной части

| Каталог | Содержание |
|---|---|
| `app/services/` | предметная логика: классификатор, опросная карта, автомат статусов, оценка, занятия, прогресс, отчёт, генерация |
| `app/api/` | точки входа HTTP: `auth`, `attempts` (АРМ-112), `operator` (Служба 112), `teacher`, `student`, `materials`, `admin` |
| `app/llm/` | провайдеры языковой модели: GigaChat, OpenAI-совместимый, заглушка |
| `app/models/` | модели SQLAlchemy 2.0 |
| `migrations/` | миграции Alembic |
| `scripts/` | разбор классификатора, расшифровка и импорт билетов, озвучивание, сравнение моделей, наполнение стенда, перевыдача карточек, замер производительности |
| `ops/backup/` | суточное резервное копирование и восстановление |

Предметная логика отделена от HTTP намеренно: разбор классификатора, автомат
статусов и оценка не зависят ни от веб-слоя, ни от базы, и проверяются
модульными тестами без поднятия приложения.

### 3.2. Клиентская часть

React 19 с TypeScript, сборка Vite. Страницы разведены по ролям; маршрутизация
одностраничного приложения. Стили собственные, без библиотек компонентов —
интерфейс следует визуальным решениям рабочей системы, а не стандартной теме
фреймворка.

### 3.3. Хранение

PostgreSQL. Четырнадцать таблиц:

| Таблица | Назначение |
|---|---|
| `app_user` | учётные записи и роли |
| `dispatch_service` | дежурно-диспетчерские службы и их названия в классификаторе |
| `scenario` | учебный сценарий: карточка происшествия вместе с эталоном |
| `training_session` | занятие: состав, нормативы, состояние |
| `attempt` | работа одного обучающегося с одной карточкой |
| `status_event` | проставленный статус с комментарием и временем |
| `evaluation` | результат оценки: балл, нарушения, замечания модели |
| `study_group` | учебная группа и её состав |
| `training_material` | методический материал справочной базы |
| `audit_event` | журнал действий пользователей |
| `error_event` | сбои приложения для отчёта администратору |
| `system_setting` | настройки комплекса, заданные из интерфейса |

Схема приводится в порядок миграциями Alembic. Прямое создание таблиц
используется только в тестах, на временной базе.

## 4. Методы обработки данных

### 4.1. Разбор Единого классификатора происшествий

Основной источник истины. Файл `classificator.xlsx` разбирается скриптом
`scripts/parse_ekp.py` в машинно-читаемый `data/ekp.json` на этапе сборки
образа; во время работы исходный файл не нужен.

Результат разбора:

| | |
|---|---|
| правил | 1283 |
| групп происшествий | 23 |
| служб реагирования | 58 |
| признаков, расширяющих список оповещения | 17 |

Каждое правило — это путь признаков, итоговый тип происшествия и перечень
служб, подлежащих оповещению. Для каждой службы указано, под каким названием
происшествие видно в её собственной системе: итоговый тип Системы-112 и тип
в системе службы могут не совпадать.

Разбор учитывает две тонкости исходного файла. Во-первых, варианты оповещения
бывают двух видов: зависящие от признака происшествия (например, «пострадавшие»)
и зависящие от канала передачи. Смешивать их нельзя — иначе список оповещения
получается неверным. Во-вторых, служебное значение «нет реагирования» означает
отсутствие реагирования, а не службу с таким названием.

Итоговый тип происшествия определяется путём признаков и не зависит от
дополнительных флагов; флаги меняют только состав оповещаемых служб.

### 4.2. Опросная карта

Из правил классификатора строится дерево опроса: группа → признак → признак →
итоговый тип. Обучающийся движется по нему так же, как оператор в рабочей
системе.

Часть признаков помечена в классификаторе как не отображаемая оператору 112 —
такие ветви из дерева исключаются, иначе тренажёр учил бы действиям, которых
в рабочей системе нет.

### 4.3. Конечный автомат статусов реагирования

Порядок статусов задан памяткой ГБУ «Система 112» и реализован таблицей
переходов. Проставить «Прибытие» до принятия заявки нельзя; карточка,
закрытая статусом завершения работ, больше не редактируется; ошибочное
«Не принята» исправляется только переходом в «Принята».

Комментарий обязателен для отказов и для завершения работ. При этом **система
не запрещает** сохранить отказ без комментария: тренажёр обязан дать
обучающемуся ошибиться, иначе нарушение `V4` никогда не возникнет и разбирать
будет нечего. Отсутствие комментария фиксируется при оценке.

### 4.4. Оценка

Оценка полностью детерминирована. Действия обучающегося сопоставляются
с эталоном, каждое расхождение даёт нарушение из каталога, балл считается
по числу и тяжести нарушений.

Каталоги нарушений воспроизводят нумерацию памятки, чтобы отчёт преподавателя
можно было сверить с первоисточником. Каждое нарушение сопровождается примером
из памятки — обучающийся видит не только «неверно», но и чем это оборачивается
на практике.

### 4.5. Роль языковой модели

Модель не выставляет балл и не определяет перечень нарушений. За ней —
единственная задача, которую нельзя решить сверкой с классификатором:
**смысловая проверка текста, введённого обучающимся**, и замечания к грамматике.
Эталонные пункты комментария задаёт сценарий, модель отвечает лишь на вопрос,
раскрыт ли каждый из них.

Такое разделение принято не из осторожности, а по результатам измерения.
Скрипт `scripts/compare_llm.py` прогоняет пятнадцать размеченных примеров
из памятки через двух провайдеров и считает отдельно два вида ошибок: ложное
замечание (пункт раскрыт, а модель говорит, что нет) и пропуск. Первая ошибка
дороже: неверный упрёк подрывает доверие ко всему разбору.

Измерение показало, что провайдеры дают разный результат на одном и том же
материале: по составу замечаний они близки, но орфографию один находит всю,
а другой не находит вовсе. Если бы от модели зависел балл, за одну и ту же
работу обучающийся получал бы разные оценки в зависимости от того, какой
провайдер включён. Поэтому балл считает классификатор.

При недоступности модели занятие идёт дальше и оценка выставляется полностью —
без смыслового разбора комментария.

### 4.6. Подготовка учебного материала

**Генерация сценариев.** Преподаватель задаёт тип происшествия, службу и
уровень сложности; модель составляет правдоподобное обращение заявителя,
адрес и перечень фактов, которые обязаны попасть в комментарий. Эталонный
статус и список оповещения при этом берутся из классификатора, а не
сочиняются моделью.

Сгенерированный сценарий не попадает к обучающимся, пока преподаватель его
не утвердил. При несогласии преподаватель вводит замечание, и сценарий
перерабатывается с его учётом.

**Экзаменационные билеты.** Расшифрованы все билеты Службы 112: 32 билета,
96 вызовов, дословно. К вызовам подобраны правила классификатора: поиск
по признакам сужает 1283 правила до двух десятков кандидатов, модель выбирает
из списка, ответ принимается только если он в этом списке — придумать
несуществующее правило она не может. Каждое сопоставление проверено человеком.

Заведено 79 вызовов: 59 на классификацию, 19 на передачу по принадлежности,
один на отказ в регистрации. Утверждено 70; девять остаются черновиками
преподавателя, где машинное сопоставление вызвало сомнение. Оставшиеся
17 вызовов эталона не имеют — модель отказалась подбирать правило, когда
подходящего не нашлось, и привязать его должен человек. Отказ здесь полезнее
выдуманного ответа: неверный эталон учит неправильному.

**Озвучивание.** Все 96 вызовов озвучены заранее (`scripts/make_audio.py`,
MP3, моно). Браузер только проигрывает готовый файл. Синтез речи средствами
браузера был опробован и отвергнут: в Firefox движок после отмены речи
остаётся в нерабочем состоянии до перезагрузки страницы, и со стороны
приложения это не лечится. Готовые записи, кроме того, отвечают требованию
технического задания к форматам аудиоматериалов.

### 4.7. Прогресс и отчётность

**Личный кабинет обучающегося** собирает по всем его занятиям: средний балл,
время до взятия карточки в работу, число опозданий, разрез по режимам
обучения, историю ошибок и список завершённых работ.

Ошибки упорядочены по тяжести последствий, а не по частоте: критическое
нарушение, встреченное дважды, важнее замечания, встреченного пять раз —
из-за первого служба не выехала бы на происшествие.

Динамика показывается начиная с шести завершённых работ. На двух-трёх
результатах разница случайна, и называть её прогрессом значило бы вводить
обучающегося в заблуждение.

Отчёт выгружается в CSV и PDF. В CSV используется разделитель «точка
с запятой» и десятичная запятая: с точкой русская локаль Excel читает баллы
как текст. В PDF вшивается шрифт с кириллицей — иначе документ, открытый
на машине без нужного шрифта, показывает пустые места вместо букв.

**Отчёт преподавателя** содержит состав требуемого техническим заданием:
действия, замечания, время заполнения карточки, отличие от норматива,
замечания к грамматике. Выводы по типичным ошибкам группы считаются
по каталогу нарушений, без обращения к языковой модели: отчёт должен
формироваться и в изолированном контуре.

### 4.8. Справочная база

Преподаватель ведёт методические материалы: инструкции, разборы, памятки.
Материал может быть написанным текстом, приложенным файлом или и тем и другим.
Черновик виден только автору — неопубликованная методичка не попадает
к обучающимся, как и неутверждённый сценарий.

Файл хранится в базе, а не в томе на диске. Комплекс работает в изолированном
контуре, материалы невелики, а резервная копия базы тогда содержит и их —
иначе восстановление вернуло бы ссылки на исчезнувшие файлы.

Принимаются документы и изображения до 10 МиБ; исполняемые файлы и архивы
отклоняются. Заявленный браузером тип не считается доказательством: он обязан
совпасть с расширением. Размер проверяется по фактически прочитанным байтам,
а не по заголовку, который клиент вправе не прислать.

### 4.9. Наблюдение за комплексом и его настройка

Администратор учебного комплекса работает из браузера: доступа к серверу,
журналам контейнеров и командной строке у него нет. Поэтому всё, что нужно
для ответа на вопрос «исправен ли комплекс», собрано на одной странице.

**Состояние.** База (отвечает ли, время отклика), языковая модель, свежесть
резервной копии, время работы приложения, нагрузка и число сбоев за сутки.
Нагрузка считается по пределам **контейнера**, а не машины: внутри контейнера
`/proc/meminfo` показывает память всего сервера, и комплекс, упирающийся
в свои 768 МБ, выглядел бы по нему занявшим десятую долю памяти. Связь
с моделью проверяется фоном не чаще раза в минуту — иначе каждый показ
страницы тратил бы лимит запросов к внешнему API.

**Сбои.** Необработанные ошибки приложения складываются в базу и группируются
по типу и сообщению. Тело запроса не сохраняется: там работа обучающегося,
а администратору она закрыта. Хранятся отдельно от журнала аудита: аудит
отвечает на вопрос «кто что сделал» и живёт не менее полугода, список
сбоев — техническая сводка, которую чистят по мере устранения.

**Конфигурация.** Провайдер языковой модели, адрес, имя модели, ключ доступа
и отключение «размышления» задаются из интерфейса и вступают в силу без
перезапуска. Это и делает выполнимым условие поставки: один и тот же комплекс
работает в изолированном контуре с локальной моделью и с внешним API.

Ключ доступа наружу не отдаётся никогда — ни при чтении, ни после сохранения,
ни в журнале аудита; виден только признак «задан». Пустое значение при
сохранении означает «не менять»: иначе администратор, поправив адрес,
случайно стёр бы ключ. Стирание — отдельное действие с подтверждением.

Кнопка проверки связи работает и на ещё не сохранённых настройках. Без неё
администратор сохранил бы неверный адрес, и смысловой разбор комментариев
молча перестал бы работать.

При выборе внешнего провайдера интерфейс прямо предупреждает, что тексты,
введённые обучающимися, уйдут за пределы учебного комплекса. Для изолированного
контура умалчивать об этом нельзя.

**Журналирование.** Уровень подробности и глубина хранения записей аудита.
Значение меньше шести месяцев задать нельзя — этого требует техническое
задание, и интерфейс объясняет отказ, а не отвергает молча.

## 5. Безопасность

- **Аутентификация** по логину и паролю, токен JWT с ограниченным сроком
  действия. Пароли хранятся в виде хеша bcrypt с предварительным
  хешированием SHA-256.
- **Разграничение доступа по ролям** проверяется на каждом обращении к API.
  Обучающийся не видит чужих работ и результатов; преподавателю прогресс
  обучающихся открыт, администратору — нет.
- **Шифрование канала** обеспечивает внешний nginx (TLS).
- **Журнал аудита** фиксирует значимые действия пользователей: входы,
  действия с учётными записями, сценарии, примечания к работам, учебные группы
  и справочную базу. Записи не удаляются: техническое задание требует
  хранения не менее шести месяцев. Логин исполнителя дублируется строкой —
  учётную запись могут удалить, а журнал обязан остаться читаемым.
- **Ограничение перебора пароля**: форма входа ограничена по частоте запросов
  на уровне nginx.
- **Работы обучающихся закрыты администратору.** Он управляет доступом
  и техническим состоянием, а результаты обучения видят только сам
  обучающийся и преподаватель. Во время идущего занятия администратор
  не может менять роль и службу его участника — это состав занятия,
  и подменять его в обход преподавателя нельзя.
- **Контейнеры** запускаются со срезанными привилегиями, с ограничениями
  памяти и процессора, файловая система интерфейса — только для чтения.
- **Резервное копирование** базы выполняется ежесуточно отдельным
  контейнером; порядок восстановления описан в `docs/backup.md`.

## 6. Установка и сборка

### 6.1. Требования к окружению

| | |
|---|---|
| Операционная система | Linux Ubuntu 20.04 и выше либо Windows 10/11 |
| Docker | 24 и выше, Docker Compose v2 |
| Память | от 2 ГБ для комплекса; для локальной языковой модели — по её требованиям |
| Браузеры | актуальные Chrome, Firefox, Яндекс.Браузер |

Отдельная установка Python, Node.js и PostgreSQL не требуется: всё собирается
в контейнерах. Для разработки нужны Python 3.12 и Node.js 22.

### 6.2. Разработка

Поднимаются база и API; переменные окружения не нужны — у всех есть
умолчания, языковая модель по умолчанию отключена.

```bash
docker compose up -d --build        # PostgreSQL и API на localhost:8000
cd frontend && npm install && npm run dev
```

Интерфейс — <http://localhost:5173>. При первом запуске создаются схема
и демонстрационные данные: идущие занятия, сценарии из памятки, билеты
Службы 112, история для личного кабинета. Учебные учётные записи: `student`,
`student2`, `teacher`, `admin`; пароль совпадает с логином, если не задан
`DEMO_PASSWORD`.

### 6.3. Установка на учебном комплексе

Продовая конфигурация добавляет контейнер с nginx, не публикует порт базы
наружу и слушает только петлевой интерфейс.

1. Создать файл `.env` рядом с `docker-compose.prod.yml`:

   ```
   DB_USER=trainer
   DB_PASSWORD=<пароль>
   DB_NAME=trainer
   SECRET_KEY=<случайная строка не короче 32 символов>
   DEMO_PASSWORD=<пароль учебных учётных записей>
   WEB_PORT=8090
   LLM_PROVIDER=stub
   ```

   Без первых пяти переменных запуск прерывается намеренно: пустой
   `SECRET_KEY` означал бы, что токены доступа можно подделать.

2. Собрать и запустить:

   ```bash
   docker compose -f docker-compose.prod.yml up -d --build
   ```

   При запуске автоматически применяются миграции и создаются
   демонстрационные данные, если база пуста.

3. Настроить внешний nginx на проксирование к `127.0.0.1:${WEB_PORT}`
   и выпустить сертификат.

4. Импортировать экзаменационные билеты (однократно):

   ```bash
   docker compose -f docker-compose.prod.yml exec backend python scripts/import_tickets.py
   ```

### 6.4. Настройка ИИ-провайдера

Контур переключается настройкой, код не меняется:

| `LLM_PROVIDER` | Назначение |
|---|---|
| `gigachat` | внешний API; требуется `GIGACHAT_AUTH_KEY` и корневой сертификат НУЦ Минцифры |
| `local` | любой OpenAI-совместимый адрес: llama.cpp, vLLM, Ollama — для изолированного контура |
| `stub` | без модели; комплекс работает, смысловой разбор комментария недоступен |

Для рассуждающих моделей предусмотрено отключение размышления
(`LLM_DISABLE_THINKING`): на проверке комментария это сокращает ответ
с 31 секунды до полутора и повышает точность. Параметр понимают llama.cpp
и vLLM, но не внешний OpenAI API, поэтому он передаётся только при явном
включении.

Полный перечень настроек с примерами — в `backend/.env.example`.

### 6.5. Обновление

```bash
docker compose -f docker-compose.prod.yml build backend web
docker compose -f docker-compose.prod.yml up -d
```

Миграции применяются автоматически при запуске. Данные сохраняются:
схема приводится в порядок миграциями, а не пересозданием.

### 6.6. Обслуживание

| Задача | Команда |
|---|---|
| Перевыдать учебные карточки перед новым показом | `python scripts/reissue.py` |
| Добавить историю обучения на работающий стенд | `python scripts/seed.py --history` |
| Импортировать билеты | `python scripts/import_tickets.py` |
| Сравнить провайдеров ИИ на размеченных примерах | `python scripts/compare_llm.py --alt` |
| Озвучить вызовы заново | `python scripts/make_audio.py --force` |
| Проверить нормативы производительности | `python scripts/loadtest.py` |
| Снять резервную копию вне расписания | `docker compose -f docker-compose.prod.yml exec backup sh /opt/backup/backup.sh` |
| Восстановиться из копии | см. `docs/backup.md` |

### 6.7. Проверка работоспособности

```bash
cd backend && python -m pytest
```

Покрыты: разбор классификатора, конечный автомат статусов, оценка обоих
режимов, опросная карта, проведение занятия, личный прогресс, отчёт,
кабинеты, провайдеры языковой модели.

Состояние работающего комплекса: `GET /api/health` (без авторизации) и раздел
«Состояние системы» в кабинете администратора.

Нормативы производительности из технического задания проверяются
`scripts/loadtest.py`. На одном узле выдержаны все четыре: отклик при ста
одновременных пользователях — 95-й процентиль 0,71 с при допустимых двух,
двадцать одновременных сессий без отказов, 237 операций записи в секунду
при требуемых ста, формирование отчёта 0,01 с при допустимых тридцати.

## 8. Условия и ограничения

Границы решения и построчная сверка каждого требования технического задания
с реализацией приведены в **приложении А**.

Кратко: комплекс не реализует голосовую связь через SIP-телефонию
(техническое задание допускает текстовую имитацию вызовов, и она дополнена
готовыми аудиозаписями); аутентификация однофакторная; управление
инфраструктурой учебного комплекса — запуск служб, обновление, резервное
копирование — выполняется системным администратором средствами операционной
системы, а не из интерфейса.
