# Резервное копирование и восстановление

ТЗ требует резервного копирования не реже раза в сутки (раздел «Общие
требования» и раздел «Надёжность») и документированной процедуры
восстановления. Здесь — как это устроено, что делать при развёртывании,
как восстановиться и как убедиться, что копии действительно снимаются.

## Кратко

| | |
|---|---|
| Что копируется | база PostgreSQL целиком: схема, данные, журнал аудита |
| Чем | `pg_dump --format=custom --compress=6` |
| Как часто | ежедневно в 00:30 UTC и один раз при каждом запуске стенда |
| Куда | том `db-backups`, внутри контейнера каталог `/backups` |
| Сколько хранится | 14 последних копий (две недели) |
| Кто запускает | контейнер `backup` в `docker-compose.prod.yml` |
| Как понять, что живо | `docker compose -f docker-compose.prod.yml ps` — контейнер `backup` в состоянии `healthy` |

## Как устроено

Отдельный контейнер `backup` на том же образе `postgres:17-alpine`, что и
база. Это осознанный выбор вместо таймера systemd на хосте: сервер общий с
другими проектами, и заводить там единицы systemd, пути и учётные данные
не нужно — всё копирование переезжает вместе с каталогом проекта и
поднимается тем же `docker compose`. Образ уже скачан для базы, поэтому на
диске он лишнего места не занимает, а версия `pg_dump` заведомо совпадает с
версией сервера (клиент младшей версии отказался бы снимать дамп).

Скрипты лежат в `ops/backup/` и монтируются в контейнер только на чтение:

- `scheduler.sh` — цикл «снять копию — доспать до следующего срока»;
- `backup.sh` — сам снимок с проверкой и ротацией;
- `healthcheck.sh` — проверка, что копии продолжают появляться;
- `restore.sh` — восстановление.

Формат `custom`, а не текстовый SQL: он сжат самим `pg_dump`, и такой архив
читается `pg_restore --list` — это позволяет проверить целостность копии,
не разворачивая её в базу. Копия стенда весит около 40 КБ, поэтому 14 копий
на диске незаметны; глубина хранения выбрана не по месту на диске, а по
времени, за которое порчу данных вообще замечают — занятия идут не каждый
день, и копия должна пережить выходные и промежуток до ближайшего разбора.

Настройки задаются в `.env` рядом с `docker-compose.prod.yml`, все
необязательные:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BACKUP_TIME` | `00:30` | время суточной копии, UTC |
| `BACKUP_KEEP` | `14` | сколько копий хранить |
| `BACKUP_MAX_AGE_HOURS` | `25` | после какого возраста последней копии контейнер считается неисправным |

## Что копирование считает своей неудачей

Молчаливый пропуск — худший вид отказа: полгода «копии делаются», а в день
аварии выясняется, что каталог пуст. Поэтому:

- дамп пишется под временным именем `.partial-*` и переименовывается в
  рабочее имя только после проверки — оборванный файл (упал контейнер,
  кончилось место) не останется в каталоге и не будет выглядеть копией;
- каждая копия сразу проверяется `pg_restore --list`; пустой, хоть и
  читаемый, архив тоже считается браком;
- при неудаче пишется отметка `/backups/last-failure` с временем и причиной,
  а следующая попытка делается через час, а не через сутки — кратковременная
  недоступность базы не должна стоить суточной копии;
- при успехе обновляется `/backups/last-success`, и `healthcheck` переводит
  контейнер в `unhealthy`, если последней удачной копии больше 25 часов.
  Отсутствие копий видно тем же способом, что и падение приложения.

## Как убедиться, что копии делаются

```bash
cd /opt/dds112
docker compose -f docker-compose.prod.yml ps backup          # ожидается healthy
docker compose -f docker-compose.prod.yml logs --tail 20 backup
docker compose -f docker-compose.prod.yml exec backup ls -la /backups
```

В логе каждая копия выглядит так:

```
[backup] 2026-09-20 00:30:01Z готово: dds112-20260920T003001Z.dump, 40.0K, объектов в архиве: 86
[scheduler] 2026-09-20 00:30:01Z следующая копия через 23 ч 59 мин
```

Причина последней неудачи, если она была:

```bash
docker compose -f docker-compose.prod.yml exec backup cat /backups/last-failure
```

## Как забрать копию с сервера

Том `db-backups` — это диск того же сервера, поэтому от потери самого
сервера он не спасает. Копию, которую нужно сохранить отдельно, забирают на
рабочую машину:

```bash
docker compose -f docker-compose.prod.yml exec -T backup \
    cat /backups/latest.dump > ./dds112-$(date +%F).dump
```

Именно `cat`, а не `docker compose cp`: `latest.dump` — ссылка на последнюю
копию, и `cp` выгрузил бы саму ссылку, а не файл. Копию с известным именем
можно забрать и так: `docker compose -f docker-compose.prod.yml cp
backup:/backups/dds112-20260920T003001Z.dump .`

## Восстановление

Процедура проверена целиком: см. раздел «Что проверено».

1. Остановить приложение, чтобы оно не писало в базу во время замены
   (обязательным не является — восстановление отцепляет чужие подключения
   принудительно, — но так у обучающихся не пропадут данные занятия,
   записанные между снимком и аварией):

   ```bash
   cd /opt/dds112
   docker compose -f docker-compose.prod.yml stop backend web
   ```

2. Посмотреть, из чего восстанавливаться:

   ```bash
   docker compose -f docker-compose.prod.yml exec backup ls -la /backups
   ```

3. Восстановить. Без имени файла берётся последняя копия; можно указать имя
   любой копии из каталога:

   ```bash
   docker compose -f docker-compose.prod.yml run --rm -e CONFIRM=yes \
       backup sh /opt/backup/restore.sh
   ```

   `CONFIRM=yes` обязателен: команда уничтожает текущее содержимое базы, и
   это не должно случаться из-за опечатки.

4. Поднять приложение:

   ```bash
   docker compose -f docker-compose.prod.yml up -d
   ```

   При старте `migrate.py` увидит актуальную схему и ничего не изменит,
   `seed.py` пропустит наполнение непустой базы — восстановленные данные
   остаются как есть.

Что делает `restore.sh`:

- проверяет архив `pg_restore --list` до того, как что-либо тронуть; на
  повреждённой копии он отказывается работать, и база остаётся прежней;
- удаляет и создаёт базу заново, а не накладывает копию поверх: при
  наложении всё, чего в копии нет (строки, добавленные после снимка;
  таблицы, удалённые миграцией), осталось бы на месте, и состояние
  получилось бы ни прежним, ни восстановленным;
- разворачивает копию с `--exit-on-error`, иначе частичное восстановление
  завершилось бы «успешно»;
- печатает число таблиц и учётных записей — быстрая проверка, что
  развернулось не пустое место.

### Восстановление на чистый сервер

Если утрачен весь сервер, а копия сохранена отдельно (см. «Как забрать
копию»), порядок такой:

```bash
git clone <репозиторий> /opt/dds112 && cd /opt/dds112
# .env с DB_USER, DB_PASSWORD, DB_NAME, SECRET_KEY, DEMO_PASSWORD
docker compose -f docker-compose.prod.yml up -d db backup
docker compose -f docker-compose.prod.yml cp ./dds112-2026-09-20.dump backup:/backups/
docker compose -f docker-compose.prod.yml run --rm -e CONFIRM=yes \
    backup sh /opt/backup/restore.sh dds112-2026-09-20.dump
docker compose -f docker-compose.prod.yml up -d --build
```

Копия разворачивается `--no-owner --no-privileges`, поэтому имя учётной
записи базы на новом сервере может отличаться от прежнего.

## Что проверено

Проверялось на локальном стенде той же конфигурации (`docker-compose.prod.yml`,
PostgreSQL 17), продовый сервер не затрагивался:

- первый запуск на пустом томе: копирование дожидается, пока приложение
  накатит миграции, и только потом снимает копию;
- расчёт расписания: после копии в 06:53 UTC следующая назначена через
  17 ч 5 мин, то есть на 23:59 UTC;
- неудача не снимает расписание: следующая попытка назначается через час;
- копия проверяемая: `pg_restore --list` показывает 86 объектов;
- ротация при `BACKUP_KEEP=3`: четвёртая копия вытеснила самую старую;
- порча данных — удалены 38 карточек, 20 оценок и 36 записей о статусах,
  обезличены и заблокированы все учётные записи, переименованы все
  сценарии, удалена таблица `session_student` целиком;
- восстановление из последней копии: содержимое всех 11 таблиц совпало с
  тем, что было до порчи, построчно (сверялось по md5 от содержимого
  каждой таблицы);
- приложение после восстановления поднимается: миграции видят актуальную
  схему, наполнение пропускается, `/api/health` отвечает;
- восстановление при работающем приложении: тоже проходит, подключения
  отцепляются принудительно;
- восстановление из копии, названной явно (не последней);
- отказ без `CONFIRM=yes` — база не тронута;
- отказ на обрезанном архиве — обнаружен до удаления базы, база не тронута;
- недоступная база: копия не снимается, в логе ошибка, записана отметка
  `last-failure`, обрезанный файл не остался;
- устаревшая копия: `healthcheck` возвращает ошибку, то есть контейнер
  уходит в `unhealthy`.

## Что нужно сделать руками при развёртывании

Ничего, кроме обычного `docker compose -f docker-compose.prod.yml up -d --build`:
контейнер `backup` поднимается вместе с остальными и снимает первую копию
сразу. Отдельно стоит:

- через несколько минут после выкладки убедиться, что `backup` в состоянии
  `healthy`;
- решить, нужна ли копия за пределами сервера, и если да — завести на
  хосте регулярное копирование `latest.dump` на другую машину.

## Чего это решение не делает

- Не защищает от потери сервера целиком: копии лежат на том же диске.
  Вынос копий наружу оставлен администратору осознанно — у учебного стенда
  нет второй площадки.
- Не даёт восстановления на произвольный момент времени (PITR): суточный
  дамп означает, что потерять можно данные до суток. Для учебного стенда
  это соответствует требованию ТЗ; для боевой Системы-112 понадобился бы
  архив WAL.
