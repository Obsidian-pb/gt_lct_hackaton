# ИИ-модуль для команды

## Главная — журнал карточек (24.09.2026)

`/teacher` и `/teacher#cards` показывают React-журнал по `card search.svg`. Источник — существующий `giik.card-workshop.v1` в браузере. Поиск учитывает номер, название, классификацию, адрес, исходную реплику и описание; фильтры — дата создания по локальному времени, группа классификатора, реальный статус `draft/approved`, округ. Доступны сортировка даты в обе стороны, 10/25/50 записей на странице и раскрытие строки. Чужие учебные статусы из примеров макета не присваиваются карточкам. Связи, ЧС, оператор и АРМ показывают прочерки, пока этих сведений нет в контракте. Назначение обучающегося пока недоступно.

«Новая карточка» ведёт в `/cards#create` с раскрытым генератором, ссылки номера/типа/деталей — в `/cards#<id>` и выбирают нужную существующую карточку. Из редактора доступен возврат в журнал. Разговор, эталоны, утверждения и прежний учебный клиент сохранены. Нет изменений Python API или схемы хранения ради нового экрана. Проверки интерфейса: `tests/check_journal_ui.mjs` и обновлённая `tests/check_teacher_ui.mjs`.

## Панель преподавателя (22.09.2026)

Начальный экран, панель и карточки перенесены в React-компоненты `frontend/src/`. Сборка esbuild сохраняется в `ui/react/app.js` и раздаётся существующим Python-сервером. Формат API, ключ localStorage и схема карточек сохранены. `/training` остаётся отдельным прежним учебным клиентом. Node.js нужен только для разработки интерфейса.

`/` — начальный экран hero.svg с прямым входом без авторизации, `/teacher` — панель преподавателя, `/cards` — прежняя мастерская в общей оболочке, `/training` — прежний учебный прототип. POST `/api` с `action=teacher_overview` возвращает проекцию сохранённых заданий и сеансов: идентификаторы, названия, статусы, вариант, имя участника и дату. Итоговая оценка включается только при `status=reviewed`; эталоны, разговоры и предварительная оценка ИИ не входят в ответ. Чтение не изменяет файлы и не вызывает модель. Это локальный стенд без ролевой авторизации; сообщения и назначение групп предстоит подключить команде.

## Зависимый классификатор (22.09.2026)

`catalog/classifier.json` содержит 1283 записи из 24 групп, включая БПЛА, и 61 службу. `tools/import_classifier.py` — воспроизводимый импорт Excel (для импорта нужен openpyxl; приложение читает готовый JSON стандартной библиотекой). SHA-256 источника, имя листа и номера строк сохранены. Все заполненные условные ячейки службы содержат столбец, текст условия и значение, включая «нет реагирования». Пустые ячейки остаются отсутствующими, не превращаются в запрет. Текст дополнительных признаков сохранён без попытки произвольно превратить его в регламент.

`card_generate` дополнительно принимает `classification` с необязательными `sign1`, `sign2`, `sign3`, `id`, `location` (до 160 символов), `flags` (ключи из metadata, значения `yes/no/unknown`). Пустой фильтр означает любой подходящий вариант. Код выбирается из согласованного пересечения фильтров; невозможное сочетание отклоняется до вызова модели. Модель получает только выбранную строку без всей матрицы служб и не определяет код сама.

Черновик может иметь пустую главную службу, если в источнике её нет либо перечислено несколько. Утверждение требует выбора преподавателя. Ответ Python-генератора содержит начальный состав из столбца M. React-мастерская дополняет его через `service-routing.js`: главные службы, заполненные безусловные ячейки и поддерживаемые условные колонки N–AG, AM, AU, CI. Варианты «признак не выбран» означают отсутствие отметки `yes`, а не утверждение об отсутствии пострадавших или угрозы. Для СМП вариант Z при пострадавших не на месте заменяет X/Y; «нет реагирования» исключает автоматическую рекомендацию данной строки. При нескольких типах берётся объединение независимых рекомендаций. Нераспознанные условия не применяются автоматически, перечисляются для проверки преподавателем; текст описания не используется для угадывания признаков.

У локальной записи карточки появился необязательный `service_selection={version:1,added:[],removed:[]}` вне `content`. Это решения преподавателя, имеющие приоритет над пересчётом при смене типов или флагов. «Вернуть автовыбор» очищает эти решения. Старые черновики получают автовыбор, дополнительные ранее выбранные службы сохраняются как ручные. Утверждённые карточки и исторические снимки не пересчитываются; после возврата на доработку автовыбор возобновляется. HTTP-контракт `content` не изменён. Автовыбор — предложение состава в редакторе, не доставка карточки и не отправка экипажей. Старые demo-коды принимаются только для совместимости существующих карточек.

Проверено 22.09.2026: 33 модульные проверки и браузерные проходы создания, редактирования, утверждения, 100 карточек, возобновления очереди и переключения веток пожар/вода. Один реальный запрос GigaChat для «Человек тонет» вернул код `17070200` и соответствующий разговор. Это проверка одного примера, не измерение точности классификации или смысловой полноты всех карточек.

## Создание карточек без учебного процесса (21.09.2026)

Нижние вкладки служб открывают сведения по службе и не меняют состав. Преподаватель изменяет состав через отдельное окно: изменения сохраняются вместе по кнопке «Применить состав», закрытие окна их отменяет. Утверждённые карточки доступны здесь только для просмотра. Это поведение React-редактора, без новых API-операций или статусов передачи службам.

`card_factory.py` — самостоятельный модуль без хранилища. `generate(provider, request)` создаёт одну карточку через существующий адаптер GigaChat. Вход: `topic` (до 3000 символов), `category` (`mixed` или строковый номер группы `1`–`24`; прежние `fire/road/medical/gas` принимаются как псевдонимы), `index` и `total` (целые, `1 ≤ index ≤ total ≤ 100`), необязательные последние 10 `recent_titles`. Одно обращение создаёт одну карточку; браузер организует очередь, остановку и повтор после ошибки. Это не фоновая задача и не идемпотентный сетевой API.

Выход: `content`, `generated_at`, `model`, `prompt_version=cards-v2.0`, `catalog_version=112-v046-24`. `content` содержит `title`, `report`, `fields`, `class_ids`, `services`, `main_service` и необязательные `flags`. Полный список полей и подписи возвращает `metadata()` и определяет `GROUPS`. Неизвестные сведения передаются явным текстом, отсутствующие служебные значения — пустыми строками. Все поля проверяются по типам, размерам и допустимым справочным значениям. Координаты парные и проверяются по диапазонам; ИИ их не генерирует. Ограничения длины проверяются локально, а не раздувают грамматику структурированного ответа провайдера.

`approve({content, reference, reference_checked, teacher, note})` проверяет обязательный минимум, актуальность эталона и явное подтверждение его проверки преподавателем. Возвращает копии карточки и эталона с отметкой преподавателя и временем. Операция не вызывает модель и не пишет файлы. Это отметка тестового интерфейса, не подтверждение полномочий пользователя. История утверждённых снимков и блокировка редактирования реализованы в локальном браузерном стенде. Будущий бэкенд команды должен обеспечивать авторизацию и неизменность версий сам.

POST `/api`: `card_meta`, `card_generate`, `card_reference`, `card_validate`, `card_approve`. Ключ GigaChat остаётся на сервере. Браузер хранит записи в `localStorage` под ключом `giik.card-workshop.v1`; экспорт содержит `format=giik-incident-cards`, `version=1`, справочник и список карточек с происхождением и историей. Не смешивать эти записи с `t-*` и `s-*` прежнего учебного движка. Импорт пока отсутствует.

Поля соответствуют обсуждаемой форме из ТЗ и замечаний к БД. Коды и признаки импортированы из предоставленного классификатора v046/24. Нормативы, реальные сведения ВИС, геокодирование, факты передачи службам и оценки генератор не создаёт. Эталон формируется отдельной операцией, описанной ниже. Семантическую согласованность исходного сообщения и полей окончательно проверяет преподаватель.

### Эталон карточки (доработка 22–23.09.2026)

С 23.09 редактор использует две вкладки одной формы по `card (1).svg`. Поля ответа изменяют только `reference.answer.expected_fields`; поля карточки — только `content`. Служебные сведения во вкладке эталона помечены как данные карточки и недоступны для редактирования. Классы, признаки и состав служб эталона отображаются из `reference.source_content`, а не из изменённой текущей карточки. Показаны номер, время создания и версия локальной карточки. С 24.09 доступны имитация АОН и текстовый разговор с заявителем; реальная телефония и учебный таймер не подключены.

`card_reference.py` принимает `content` и возвращает `reference` версии 1: снимок `source_content`, `answer`, сведения о модели, времени и версии промпта. В `answer` входят 25 полей `expected_fields` с `value` и `evidence`, краткий ответ, обоснование классификации и служб, вопросы для уточнения и критичные ошибки. Служебные регистрационные поля, координаты и ВИС не генерируются. GigaChat получает исходное сообщение и пронумерованные фрагменты; выбирает `source_id`, а код подставляет дословную цитату. Для известных значений ссылка обязательна. Совпадение цитаты с источником не доказывает смысловую правильность значения — это проверяет преподаватель. Допускается одна повторная попытка исправить структуру; сетевые ошибки возвращаются пользователю.

React после каждой созданной карточки и автовыбора служб вызывает `card_reference`. Ошибка не удаляет карточку или прежний эталон; доступна отдельная повторная генерация. Ответ редактируется преподавателем, подтверждается флажком и утверждается вместе с карточкой. Изменение карточки делает эталон неактуальным; проверка выполняется также на сервере. Предыдущие ответы и утверждённые снимки сохраняются в истории. Старые утверждённые карточки без эталона остаются доступными; для добавления ответа их нужно вернуть на доработку. Эталоны этого редактора пока не подключены к прежним учебным сеансам и их оцениванию. Локальный стенд по-прежнему не предоставляет ролевую авторизацию.

Проверено 21.09.2026: 27 модульных проверок; браузерный проход с тестовой моделью (1 и 100 карточек, повтор ошибки, остановка, перезагрузка, утверждение и история, экспорт, мобильная ширина) и регрессия прежних двух учебных вариантов. На GigaChat-2-Pro три примера «пожар / ДТП / медицина» прошли проверку схемы; дополнительно одна медицинская карточка создана через браузер. Это небольшая ручная проверка, не оценка точности модели на представительном наборе. Первоначальная схема с большими maxLength дважды не дождалась ответа; после переноса ограничений в локальную валидацию генерация завершилась. Промпт уточнён после обнаружения деталей вне исходного сообщения и неподтверждённой медицинской интерпретации. Такие смысловые расхождения всё ещё возможны (например, этаж может быть указан в полях и пропущен в сообщении), поэтому автоматического утверждения нет. Настройки генерации: temperature 0.65, max_tokens 4500 в существующем адаптере.

Реализация — Python, провайдер GigaChat. `ai_core.Engine` и `dds.py` содержат поведение модели и учебного сценария. Локальный веб-интерфейс и консоль — стенды проверки. Учётные записи, права, SIP, реальная телефония, постоянная база общего проекта и распределение групп реализуются командой отдельно.

## Два варианта одного обучающегося

| workflow | Начальные данные | Собеседник модели |
|---|---|---|
| `caller` | Первая реплика, пустая карточка | Заявитель / очевидец |
| `dds` | Заполненная карточка 112, доступное уточнение | Сотрудник учебной службы |

Старые задания без `workflow` считаются `caller`. Оба варианта работают с одним именем обучающегося и общей историей его работ. В готовом продукте идентификацию и проверку полномочий обеспечивает бэкенд, не LLM.

## Операции

```python
engine.draft(topic, level, workflow="dds")  # Черновик сценария и эталона от GigaChat.
engine.sample(level="medium", workflow="dds")  # Встроенный пример для проверки.
engine.approve(task_id, teacher)  # Только после просмотра преподавателем.
view = engine.start_assigned(student, workflow="dds")
engine.connect_service(view["id"])
engine.ask(view["id"], "Представляюсь и передаю сообщение", source="text")
engine.set_field(view["id"], "address", "Уточнённый адрес")
engine.set_channel(view["id"], "drop")
engine.ask(view["id"], "Эта фраза не дойдёт")
engine.connect_service(view["id"])  # Перезвон с сохранением услышанного.
engine.ask(view["id"], "Повторяю недоставленное сообщение", source="voice")
engine.submit(view["id"])
report = engine.assess(view["id"])  # Только преподавателю.
```

`connect_service` и `set_channel` — переходы учебного состояния, не операции SIP. Внешний модуль телефонии может сообщать им о соответствующих событиях. В прототипе их вручную вызывает тестирующий пользователь. Перед интеграцией следует согласовать схему реальных событий доставки аудио, идентификаторы реплик и повторных запросов; текущие операции не являются идемпотентным сетевым API.

## Входящий сценарий ДДС

- `incoming_card`: семь исходных заполненных полей. Версия сохраняется в сеансе независимо от исправлений ученика.
- `verification_notes`: доступный ученику источник для обнаружения ошибки. Источник является учебным материалом, его не следует выдавать за интеграцию с реальной 112.
- `service`: имя службы, роль и знания до звонка. Здесь нельзя указывать скрытые ответы или сведения о происшествии, которых служба ещё не получила.
- `persona`: характер сотрудника, без скрытых фактов происшествия.
- `faults`: описание заложенных ошибок, только преподавателю.
- `fields`: эталон итоговой карточки и критерии полей.
- `actions`: эталон проверки карточки, передачи сведений, подтверждения приёма и действий при обрыве.

Это редактируемые учебные условия. Они не объявляются реальным регламентом служб и требуют подтверждения преподавателем. В этой версии семь полей временные; переход на окончательную форму потребует согласованной схемы с командой.

## Память собеседника и связь

Состояния ДДС: `idle → connected → disconnected/ended → connected`. После сдачи упражнения звонок закрывается.

Следующая реплика может передаваться:

- `clear`: целиком;
- `partial`: доставляется только первая половина слов; модель просит повторить недостающее;
- `drop`: сообщение не доставляется вообще, соединение обрывается; GigaChat для потерянной реплики не вызывается;
- `hangup`: отдельное завершение звонка диспетчером.

Это **текстовая модель доставки**, а не акустический шум или эмуляция потери сетевых пакетов. Направление помех в первой версии — от диспетчера к службе. Аудиоэффекты и обратное направление можно подключить позднее через внешнюю телефонию.

У реплики диспетчера в истории сохранены `text` (сказанное), `delivered` (дошедшее), `delivery` (`full`, `partial`, `lost`), `source` и время. В запрос GigaChat для службы попадают только `delivered` и ранее сказанные реплики службы. Исходная карточка, ручные правки ученика, эталон и полный текст недоставленных сообщений туда не передаются.

Если GigaChat недоступен, реплика и помеха не считаются успешно обработанными; пользователь может повторить запрос. Техническая ошибка провайдера не подменяется учебным обрывом и не становится ошибкой ученика.

## Проверка

`caller`: семь критериев полей.

`dds`: семь критериев полей плюс `action_validation`, `action_transmission`, `action_confirmation`, `action_recovery`.

ИИ получает исходную и итоговую карточки, утверждённый эталон, доступное уточнение, историю доставки и количество подсказок. Критерий восстановления связи программно помечается неприменимым, если в упражнении не было события обрыва. Частичная слышимость сама по себе не считается полным обрывом.

Проверяются дословные ссылки на доставленные фрагменты диспетчера и реплики службы. Неподтверждённые цитаты удаляются с предупреждением преподавателю. Это проверка происхождения цитат, а не гарантия правильности выводов LLM.

Для `finalize()` преподаватель должен рассмотреть все 11 критериев ДДС, указать собственную оценку и комментарий. До этого `student_view()` не возвращает предварительное заключение, эталон или скрытое описание ошибок.

## Проверки и ограничения стенда

`python -m unittest discover -s tests -v` — сценарии, состояние связи, отсутствие утечки потерянных слов, старые задания, оценка преподавателем.

`python smoke_dds_live.py` — реальные запросы GigaChat в отдельном `test-output/`: создание ДДС-сценария, обрыв, перезвон, передача, предварительная проверка.

`tests/check_web_ui.mjs` — автоматический проход обоих вариантов в браузере с тестовой моделью; требует Playwright.

Окончательный вывод о педагогической корректности задания и реплик остаётся за преподавателем. Модель может ошибаться; отделение контекстов ограничивает доступ к скрытым данным, но не исключает выдуманных ответов.
# Условный АОН в браузерном стенде

При создании карточки приложение один раз задаёт `content.fields.phone_aon` в вымышленном формате `+7 (000) XXX-XX-XX`; `telephony.mode = "simulated"` отмечает имитацию. Это метаданные приложения, не ответ GigaChat и не реальное определение номера. АОН сохраняется вместе с карточкой, доступен только для чтения и не меняется при обновлении страницы или эталона.

`phone_callback` и `phone_scene` — независимые строки. С 24.09 у новых карточек обратный телефон изначально пуст, ввод доступен после уточнения в разговоре. Копирование из АОН убрано. Произвольный ручной ввод сохраняется без скрытой замены цифр. АОН не является доказательством произнесённого номера.

У старых черновиков заменяются только пустой АОН и прежняя заглушка «Не определён: вымышленная карточка». Миграция записывается в историю и снимает подтверждение эталона. Утверждённые карточки, введённые ранее номера, эталоны и исторические снимки не изменяются.

## Разговор и скрытый телефон (24.09.2026)

В новой карточке браузер создаёт отдельный `caller_scenario={version:1,phone_callback}` с постоянным вымышленным номером, отличным от АОН. Номер не добавляется в исходную реплику или заполняемое поле. Для старых черновиков предусмотрена явная кнопка «Подготовить разговор»: прежние введённые значения сохраняются, эталон требует обновления. Старые утверждённые карточки необходимо сначала вернуть на доработку.

`card_reference` и `card_approve` принимают необязательный `caller_scenario`. Эталон сохраняет его в `source_scenario`; изменения проверяются на актуальность наряду с `source_content`. Код подставляет точный телефон в `expected_fields.phone_callback` со свидетельством «Сведения сценария заявителя: ...». Это известный автору факт сценария, **не цитата уже услышанной реплики**. Остальные поля сохраняют прежнюю проверку источника. Без сценария прежний контракт остаётся действующим.

`card_caller` принимает `{content,caller_scenario,turns,question}` и возвращает `{reply,callback_disclosed,prompt_version}`. История состоит из чередующихся `{role:dispatcher|caller,text}` (до 30 вопросов). GigaChat получает исходные обстоятельства и историю, без редактируемых полей и эталона. Модель определяет смысл вопроса и отвечает по известным обстоятельствам; точные цифры телефона подставляет приложение только при запросе перезвона. Неизвестные обстоятельства запрещено додумывать. Проверка телефонных цифр ограничивает выдумывание номера, но не гарантирует смысловую точность всех реплик модели.

Браузер сохраняет отдельную историю `caller_dialogue`, открывает ввод телефона после раскрытия и не заполняет его автоматически. Повторный вопрос возвращает тот же номер. Ошибка модели не добавляет реплики; вопрос остаётся для повторной отправки. Разговор сам по себе не меняет карточку, эталон и отметку проверки. Это предварительный просмотр для преподавателя в локальном стенде без разграничения доступа; в будущем ученическому клиенту нельзя передавать `caller_scenario` и эталоны. Прежний `/training` продолжает использовать свои независимые задания. Голосовой ввод прежнего прототипа не перенесён в этот новый текстовый блок.

Проверено: 42 модульных теста, браузерный сценарий скрытого телефона/ручного ввода/ошибки/сохранения/эталона и три последовательных вопроса реальному GigaChat (номер дома, телефон для перезвона, повтор телефона). Это небольшая проверка, не оценка общей точности диалога.
