# Общий сервер тренажёра 112 — PostgreSQL

Эта сборка поддерживает два режима хранения:

- **локальный/настольный** — прежние JSON + SQLite, чтобы проект можно было запускать без инфраструктуры;
- **общий сервер** — PostgreSQL как единый источник данных для всех компьютеров.

Для реального занятия на нескольких компьютерах используйте **только общий серверный режим**.
Фронтенд продолжает работать с тем же `/api/v1`; менять URL и форматы существующих карточек не нужно.

## Что хранится в PostgreSQL

Миграции находятся в `migrations/` и создают:

- `app_users` — серверные пользователи и системные роли;
- `auth_sessions` — задел под серверные сессии авторизации;
- `engine_items` — задания и работы обучающихся;
- `session_results` — проекция результатов/оценок для отчётности;
- `curriculum_resources` — сценарии и тренировки;
- `scenario_tasks`, `training_scenarios`, `training_tasks` — связи учебного плана;
- `training_participants` — участники и учебные роли operator/dds/service;
- `training_cards` — карточки, передаваемые между рабочими местами;
- `training_events` — серверный журнал снимков/событий тренировки;
- `materials` — общие методические материалы;
- `workshop_states` — черновики и состояние мастерской карточек преподавателя;
- `system_settings` — общие настройки админ-панели;
- `schema_migrations` — версия схемы.

Гибкие поля карточек и сценариев сохраняются в `jsonb`, но основные связи, роли,
статусы, пользователи и результаты вынесены в отдельные колонки/таблицы.

## Быстрый запуск на Windows-сервере с Docker Desktop

1. Запустите `SETUP_SHARED_SERVER.cmd`.
2. Скрипт создаст `.env.server`, поднимет PostgreSQL 16 и применит миграции.
3. Если в старой папке `data` уже есть карточки/тренировки/пользователи, выполните один раз:

```powershell
py -3 manage_db.py import-legacy --data-dir data
```

Импорт **не выполняется автоматически при старте**, чтобы случайно не перезаписать рабочую БД.
Для осознанного объединения с уже заполненной базой добавьте `--merge`.

4. Запустите `START_SHARED_SERVER.cmd`. Если база пуста, скрипт запросит пароль
   для первой учётной записи `admin` (минимум 10 символов) и продолжит запуск.
   Пароль не попадает в историю команд. Если вы импортировали пользователей,
   но администратора среди них нет, создайте его через `manage_users.py create`.

Сервер слушает `0.0.0.0:8878` в локальной сети; AI REST поднимается только локально на `127.0.0.1:8890`. Перед запуском автоматически пересобирается React-интерфейс из `frontend/src`.

## Внешний PostgreSQL без Docker

Создайте базу и пользователя у провайдера/администратора PostgreSQL, затем задайте:

```text
DATABASE_URL=postgresql://USER:PASSWORD@DB_HOST:5432/DB_NAME
```

Можно хранить эту строку в `.env.server` (файл не надо публиковать) или в системной
переменной окружения. Затем:

```powershell
py -3 -m pip install -r requirements-server.txt
py -3 manage_db.py migrate
START_SHARED_SERVER.cmd
```

Первый запуск предложит создать администратора, если база пуста.

## Пользователи и роли

Системные роли: `admin`, `teacher`, `student`.
Учебные роли внутри конкретной тренировки: `waiting`, `operator`, `dds`, `service`.
Это разные уровни: администратор системы может при необходимости иметь отдельный учебный профиль.

Создание пользователя:

```powershell
py -3 manage_users.py create ivanov "Иванов Иван" student
```

Список:

```powershell
py -3 manage_users.py list
```

Смена системной роли/имени или блокировка:

```powershell
py -3 manage_users.py update 3 --role teacher
py -3 manage_users.py update 3 --disable
py -3 manage_users.py update 3 --enable
```

Сброс пароля:

```powershell
py -3 manage_users.py password 3
```

Те же операции доступны администратору прямо в интерфейсе **Администратор → Пользователи** и через серверный API:

- `GET /api/v1/accounts`
- `POST /api/v1/accounts`
- `GET /api/v1/accounts/me`
- `PATCH /api/v1/accounts/{id}`
- `POST /api/v1/accounts/{id}/password`

Самостоятельную регистрацию обучающихся можно включить:

```text
ALLOW_SELF_REGISTRATION=1
```

После этого `POST /api/v1/accounts/register` создаёт **только** роль `student`.
По умолчанию регистрация выключена.

## Проверка, что сервер действительно работает с PostgreSQL

Откройте:

```text
http://IP_СЕРВЕРА:8878/api/v1/health
```

В ответе должно быть:

```json
{
  "data": {
    "status": "ok",
    "storage": {
      "backend": "postgresql",
      "schema_version": 5
    }
  }
}
```

Если там `backend: files`, запущен локальный режим, а не серверный PostgreSQL.
`START_SHARED_SERVER.cmd` запускается с `--require-postgres`, поэтому при неверной
настройке БД он завершится ошибкой вместо тихого отката на JSON.

## Доступ с разных компьютеров

Все рабочие места открывают **один и тот же адрес сервера**, например:

```text
http://192.168.1.50:8878/
```

Каждый входит своей серверной учётной записью. Карточки, черновики мастерской, комнаты, роли, материалы, результаты и состояние тренировки читаются из одной PostgreSQL БД, поэтому действия одного ПК видит другой после обычного обновления/опроса API.

В серверном режиме администратор создаёт пользователей, меняет системные роли, блокирует учётные записи и сбрасывает пароли в **Администратор → Пользователи**. Учебная роль (`operator`, `dds`, `service`) остаётся отдельной и задаётся для конкретной тренировки.

Если у преподавателя до перехода на сервер были карточки в `localStorage`, при первом открытии `/cards` под его серверной учётной записью и пустой серверной мастерской этот локальный набор используется как исходный и синхронизируется в PostgreSQL. После этого PostgreSQL является источником данных для мастерской на других компьютерах.

## Публикация в интернете

Не выставляйте встроенный HTTP-сервер напрямую в интернет. Запускайте приложение на
внутреннем интерфейсе/localhost за Nginx, Caddy или другим reverse proxy с HTTPS.
Укажите:

```text
PUBLIC_ORIGIN=https://trainer.example.org
```

Пароли текущего совместимого режима передаются через HTTP Basic, поэтому HTTPS обязателен.
Также ограничьте прямой доступ к PostgreSQL: порт 5432 не должен быть открыт пользователям.

## Резервное копирование

Резервировать нужно PostgreSQL, а не папку `data`:

```powershell
pg_dump -Fc "$env:DATABASE_URL" -f trainer112.backup
```

Папка `data` после успешного импорта может оставаться как архив прежнего локального режима, но серверный процесс её не использует для общих учебных данных. Браузерный `localStorage` в серверном режиме остаётся только кэшем/настройками интерфейса и черновиком ещё не сохранённой формы обучающегося; авторитетные карточки, учётные записи и результаты находятся на сервере.

## Что не происходит автоматически

- старые JSON/SQLite не импортируются при каждом запуске;
- миграции схемы не удаляют пользовательские данные;
- `config.local.json` с ключом AI Tunnel остаётся серверным секретом и не отправляется браузерам;
- PostgreSQL не хранит модели Piper `.onnx`: это серверные файлы приложения, а не пользовательские данные.

## Вход преподавателей и обучающихся

В общей серверной версии преподаватели и обучающиеся больше не используют локальный профиль браузера как учётную запись. Администратор создаёт им логин, пароль и системную роль в разделе **Пользователи**.

Стартовая страница направляет пользователя на `/login`. После успешной проверки данных сервер создаёт защищённую сессию и открывает соответствующую панель:

- `teacher` → `/teacher`;
- `student` → `/student`;
- `admin` → `/admin`.

Пароли хранятся только в виде PBKDF2-хеша. Активные браузерные сессии хранятся в PostgreSQL (`auth_sessions`). Блокировка учётной записи или изменение пароля отзывает её активные сессии.

Системная роль пользователя и учебная роль в тренировке — разные сущности. Пользователь с системной ролью `student` может быть назначен в тренировке оператором 112, диспетчером 112 или диспетчером службы.

Подробная инструкция: `AUTH_ROLES.md`.
